# Metabase query engine

The native query engine: Apache DataFusion wrapped in a small Rust workspace, loaded into the
Metabase JVM in production and run as a sidecar during development. The design, rationale, and
milestones are in [`dev/notes/datafusion-engine.md`](../dev/notes/datafusion-engine.md).

## Layout

| Crate                              | What it is                                                                      |
| ---------------------------------- | ------------------------------------------------------------------------------- |
| `crates/engine-core`               | The engine: JSON message API, catalog snapshots, planner, connector trait       |
| `crates/engine-dialects`           | Unparser dialects and per-warehouse capability policy                           |
| `crates/engine-ffi`                | The C ABI (`libmetabase_engine`), loaded from Clojure through Panama and coffi  |
| `crates/engine-server`             | The development sidecar: the same core behind Arrow Flight                      |
| `crates/engine-connectors/*`       | Warehouse connectors (Postgres; the JDBC bridge stub)                           |
| `include/metabase_engine.h`        | Generated by cbindgen on every build of `engine-ffi`                            |

## Build and test

```
cd engine
cargo build            # produces target/debug/libmetabase_engine.{dylib,so}
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all
```

`cargo test` alone does not rebuild the shared library; run `cargo build` first when the Clojure
tests or the dlopen test need a fresh one.

The toolchain is pinned in `rust-toolchain.toml`; rustup installs it on first use.

## Use it from Metabase

The Clojure module is `metabase.engine.*`. It finds the library in this order: the
`engine-native-library-path` setting or `MB_ENGINE_NATIVE_LIBRARY_PATH`, the copy bundled in the
jar under `native/metabase-engine/<os>-<arch>/`, then `engine/target/{debug,release}` for
development. The JVM needs `--enable-native-access=ALL-UNNAMED`, which the `:dev` and `:test`
aliases and the Docker start script already pass.

```clojure
(require '[metabase.engine.core :as engine])
(engine/version)
(engine/register-catalog! {:database_id 1 :catalog_version "v1" :connector "postgres"
                           :tables [{:schema "public" :name "orders"
                                     :columns [{:name "id" :type "Int64" :nullable false}]}]})
(engine/with-session [s {:database_id 1}]
  (engine/plan-and-unparse s "SELECT \"id\" FROM \"public\".\"orders\" LIMIT 5"))
```

Run the module's tests from a REPL with `(clojure.test/run-tests 'metabase.engine.core-test)`, or
`./bin/test-agent :only '[metabase.engine.core-test]'`.

## Run the sidecar

```
cargo run -p engine-server -- --listen 127.0.0.1:50051 --log info
```

It speaks Arrow Flight. The `call` action carries the same JSON envelope as `mb_engine_call`;
`DoGet` will stream results once execution lands. Point Metabase at it with
`MB_ENGINE_TRANSPORT=sidecar` (the Clojure client arrives with the Arrow dependencies in milestone 3).

## Conventions

- Rust never sees MBQL. It receives DataFusion SQL plus a session context.
- The pushed plan is analyzed, never optimized, before unparsing.
- Every C ABI export catches panics and reports them as a structured error with code 2.
- Errors carry `error_type`, the exact `metabase.query-processor.error-type` keyword.
- Bump `datafusion`, `arrow`, `arrow-flight`, and `tonic` together.
