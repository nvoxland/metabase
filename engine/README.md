# Metabase query engine

The native query engine: Apache DataFusion wrapped in a small Rust workspace, loaded into the
Metabase JVM in production and run as a sidecar during development. The design, rationale, and
milestones are in [`dev/notes/datafusion-engine.md`](../dev/notes/datafusion-engine.md).

## Layout

| Crate                        | What it is                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------ |
| `crates/engine-core`         | The engine: JSON message API, catalog snapshots, planner, connector trait      |
| `crates/engine-dialects`     | Unparser dialects and per-warehouse capability policy                          |
| `crates/engine-ffi`          | The C ABI (`libmetabase_engine`), loaded from Clojure through Panama and coffi |
| `crates/engine-server`       | The development sidecar: the same core behind Arrow Flight                     |
| `crates/engine-connectors/*` | Warehouse connectors (Postgres; the JDBC bridge stub)                          |
| `include/metabase_engine.h`  | Generated by cbindgen on every build of `engine-ffi`                           |

## Build and test

```
cd engine
cargo build            # produces target/debug/libmetabase_engine.{dylib,so}
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all
```

`cargo test` alone does not rebuild the shared library; run `cargo build` first when the Clojure
tests or the dlopen test need a fresh one.

The toolchain is pinned in `rust-toolchain.toml`; rustup installs it on first use.

## Use it from Metabase

The Clojure module is `metabase.engine.*`. It finds the library in this order: the
`engine-native-library-path` setting or `MB_ENGINE_NATIVE_LIBRARY_PATH`, the copy bundled in the
jar under `native/metabase-engine/<os>-<arch>/`, then `engine/target/{debug,release}` for
development. The JVM needs `--enable-native-access=ALL-UNNAMED`, which the `:dev` and `:test`
aliases and the Docker start script already pass.

```clojure
(require '[metabase.engine.core :as engine])
(engine/version)
(engine/register-catalog! {:database_id 1 :catalog_version "v1" :connector "postgres"
                           :tables [{:schema "public" :name "orders"
                                     :columns [{:name "id" :type "Int64" :nullable false}]}]})
(engine/with-session [s {:database_id 1}]
  (engine/plan-and-unparse s "SELECT \"id\" FROM \"public\".\"orders\" LIMIT 5"))
```

Run the module's tests from a REPL with `(clojure.test/run-tests 'metabase.engine.core-test)`, or
`./bin/test-agent :only '[metabase.engine.core-test]'`.

## Run the sidecar

```
cargo run -p engine-server -- --listen 127.0.0.1:50051 --log info
```

It speaks Arrow Flight. The `call` action carries the same JSON envelope as `mb_engine_call`, and
`DoGet` streams a statement's batches for a session created through `call`. Point Metabase at it
with `MB_ENGINE_TRANSPORT=sidecar` (and `MB_ENGINE_SIDECAR_URL` if not `http://localhost:50051`).
Because the JVM can't reload a native library, this is the way to pick up engine changes without
restarting the REPL.

## Packaging

`./bin/build.sh` has an `:engine` step (`bin/build/src/build/engine.clj`) that runs
`cargo build --release -p engine-ffi` for the host and copies the library to
`resources/native/metabase-engine/<os>-<arch>[-musl]/`, which the uberjar picks up like any other
resource. `SKIP_ENGINE_NATIVE=true` skips it; without `cargo` on the path it warns and the jar ships
without the engine, in which case `engine.init` keeps every database on the JDBC path. Libraries
already present under `resources/native/metabase-engine/` are used as-is, so CI can place the
per-platform builds from `.github/workflows/engine.yml` there before building the jar.

The Alpine image needs `libgcc` (added to `bin/docker/Dockerfile`) because a musl build without
`crt-static` links `libgcc_s` dynamically. The `build-native` matrix in the engine workflow builds a
`linux-x86_64-musl` library, but nothing places it in the jar yet: until that plumbing exists the
image starts without the engine and routing keeps every database on JDBC.

## The JDBC bridge

Warehouses without a good Rust driver are reached through `crates/engine-connectors/jdbc-bridge`: a
Flight client for a small service Metabase hosts over its own JDBC pools
(`metabase.engine-bridge.core`, loopback only, token in every ticket). The engine still plans and
unparses; the bridge only executes the warehouse SQL and streams Arrow batches back. Turn it on with
`MB_ENGINE_BRIDGE_ENABLED=true` and list the engines it serves in `MB_ENGINE_BRIDGE_WAREHOUSES`
(comma separated); a database whose engine is listed registers with the `jdbc-bridge` connector
instead of a native one. The dialect still comes from the catalog snapshot, so only warehouses the
engine has a dialect for can be bridged.

## Conventions

- Nothing runs on the caller's thread. The C ABI hands every request to the engine's worker
  threads through `Engine::run_on_runtime` and waits; result streams are produced by a worker task
  and consumed over a channel. JVM threads have small stacks and the planner recurses deeply.
- Code reachable from an Arrow C-stream callback (`get_next`, `release`) catches panics and does not
  assume a tokio context: hold a runtime `Handle` for cleanup.
- Postgres statements run with `default_transaction_read_only = on`; session settings are `SET` on
  checkout and `RESET` before the connection returns, on success and on failure.
- Rust never sees MBQL. It receives DataFusion SQL plus a session context.
- The pushed plan is analyzed, never optimized, before unparsing.
- Every C ABI export catches panics and reports them as a structured error with code 2.
- Errors carry `error_type`, the exact `metabase.query-processor.error-type` keyword.
- Bump `datafusion`, `arrow`, `arrow-flight`, and `tonic` together.
